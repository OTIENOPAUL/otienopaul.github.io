The problem

Loan teams need to estimate whether an applicant may struggle to repay. Reviewing every application by hand is slow and inconsistent, and a rigid rule misses real differences between applicants.

The data adds a second difficulty: defaults are a small minority of applications. A model that simply predicts “repays” would look accurate while failing at the one job that matters.

How I solved it

  1. Framed the task as binary classification on the Home Credit Default Risk benchmark: predict the probability that an applicant will have payment difficulties.
  2. Trained a regularized LightGBM model and handled the class imbalance so the rare default class is not drowned out.
  3. Audited the model with SHAP to see which applicant features push a score up or down.
  4. Saved the model with its expected feature list, then built a Streamlit app that rebuilds a full input row from a handful of applicant fields in the exact column order the model expects.
  5. Debugged inference. A LightGBM categorical-feature mismatch surfaced in the app; passing the ordered input as a NumPy array fixed it.
  6. Deployed the app publicly so anyone can test applicant profiles.

The outcome

  • A Streamlit underwriting simulator prototype. Visitors adjust external credit scores, annual income, requested loan amount, monthly annuity, employment duration and age, and get a predicted default probability instantly.
  • A transparent decision rule. The app compares the probability with a 12% threshold and returns an approve or review message. The sample profile shown scores 11.64% and is approved.
  • Project artifacts: The linked repository contains a notebook, Streamlit app and saved model artifacts. This is a portfolio demo, not validated lending decision support.

Next steps

Next steps

The project notes report validation ROC-AUC and PR-AUC, but the data and implementation are not present in this portfolio repository for independent review. The sample score and 12% threshold are demonstration values, not validated lending policy. Add an evaluation protocol, calibration, fairness analysis and threshold rationale before presenting the model as decision support.
